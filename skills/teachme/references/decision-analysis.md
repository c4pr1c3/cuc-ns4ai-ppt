# 关键技术决策点评维度

针对"关键技术决策的点评与建议"场景的补充指南。

## 决策点评 vs 方案选型的区别

| 维度 | 方案选型 | 决策点评 |
|------|----------|----------|
| 时间点 | 决策前 | 决策后（或决策中） |
| 目标 | 选择最优方案 | 评估决策质量，提取经验教训 |
| 视角 | 面向未来 | 面向过去（复盘）或面向现在（评审） |
| 输出 | 推荐方案 + 决策树 | 评价 + 改进建议 + 可复用的决策原则 |

## 点评框架：DECIDE

### D - Decision Context（决策背景）

首先还原决策的完整背景，避免事后诸葛亮：
- **当时的信息条件**：决策者掌握了哪些信息？有哪些信息是后来才出现的？
- **当时的约束**：时间压力、资源限制、组织政治、技术债
- **决策者的目标**：他们当时真正优化的是什么？（不一定是"技术最优"，可能是"风险最低"、"交付最快"或"团队士气"）
- **可选项范围**：当时有哪些真实的可选项？"为什么不选 X"可能是因为 X 当时还不存在。

**原则**：评价一个决策，必须用决策时的信息条件，而不是现在的信息。

### E - Expected Outcome（预期 vs 实际）

- 决策时的预期结果是什么？
- 实际结果如何？偏差在哪里？
- 偏差是源于决策本身，还是源于执行过程，还是源于外部变化？

### C - Consequences（影响分析）

分析决策的连锁影响：
- **直接影响**：对目标系统的影响
- **间接影响**：对相关系统、团队、流程的影响
- **长期影响**：技术债积累、团队能力变化、未来选项的增减
- **意外后果**：有没有意料之外的正面或负面影响？

### I - Improvement（改进建议）

面向未来给出可操作的改进建议：
- **如果是类似决策**：下次应该怎么做不同？
- **如果决策已定**：如何 mitigate 负面影响？如何放大正面影响？
- **流程改进**：决策过程本身有什么可以优化的？（是否需要更多 stakeholder 参与？是否需要更长的评估期？）

### D - Documentation（原则提取）

将具体决策抽象为可复用的原则：
- "在 X 条件下，优先考虑 Y"
- " stakes 超过 Z 时，必须包含 W 评估维度"
- "当存在 A 和 B 两个冲突目标时，以 C 为准"

### E - Expression（表达方式）

根据用户的目标调整点评的语气和深度：
- **事后复盘**：客观、建设性，聚焦"我们能学到什么"
- **同行评审**：技术深度，聚焦设计正确性和完整性
- **向上汇报**：简洁、有结论，聚焦风险和建议
- **自我反思**：坦诚，聚焦认知盲点和改进方向

## 网络安全场景的特殊考量

在网络安全领域，决策点评需要额外关注：

1. **威胁模型是否完整**：决策时考虑的威胁面是否足够？有没有忽略新兴攻击向量？
2. **安全与可用性的权衡**：安全措施是否过度影响了用户体验或系统性能？
3. **纵深防御**：是否依赖单一安全机制？有没有多层防护？
4. **合规性**：决策是否符合相关安全标准和法规要求？
5. **事件响应准备**：如果安全决策被突破，检测和响应机制是否就绪？
6. **供应链安全**：第三方依赖的安全风险是否被评估？

## 点评语气指南

| 场景 | 语气 | 示例 |
|------|------|------|
| 团队内部复盘 | 建设性、反思性 | "当时的约束让我们选择了 X，但如果能提前做 Y 验证，可能会发现..." |
| 评审他人设计 | 尊重但直接 | "这个设计在 Z 场景下可能会出现问题，建议考虑..." |
| 向上汇报风险 | 简洁、有数据 | "当前决策在 A 条件下有 B 风险，建议 C  mitigation 措施" |
| 学术/论文评审 | 严谨、引用 | "作者选择 X 方法的动机合理，但缺少对 Y 局限性的讨论..." |
